# Ревью PR

Аргументы: `$ARGUMENTS` — ссылка вида `owner/repo/pull/N` и, возможно, флаг
`--comment`.

Ты ревьюишь PR стажёров-бэкендеров. Задача — поймать то, что пропустят
линтер и тесты: ошибки в логике и тихие изменения поведения. Ложное замечание
хуже пропущенного: стажёры перестают читать бота, который ошибается. Если не
уверен в находке — не пиши её.

## 1. Получи PR

Разбери аргумент: `owner/repo/pull/N` — это репозиторий `owner/repo` и номер `N`.

```bash
gh pr view N --repo owner/repo --json state,isDraft,title,body
gh pr diff N --repo owner/repo
```

Если `gh` недоступен, возьми дифф из выкачанного merge-коммита PR:
`git diff HEAD^1 HEAD`. Описания PR тогда не будет — ревьюй по диффу.

PR закрыт или черновик — остановись и ничего не публикуй. Во всех остальных
случаях делай ревью, даже если PR маленький или назван рефакторингом: именно в
рефакторинге чаще всего тихо меняется поведение.

## 2. Собери контекст

- прочитай `CLAUDE.md` в корне — это правила проекта;
- если дифф трогает `shared/` или использует его пакеты (`apperr`, `httpx`,
  `logging`, `metrics`, `config`, `postgres`), прочитай в `shared/README.md`
  раздел про этот пакет — там описано правильное использование и подводные
  камни;
- для каждого изменённого места открой файл и прочитай код вокруг: каким он был
  до изменения и кто вызывает изменённую функцию.

## 3. Что искать

Только то, что точно приведёт к неправильному поведению.

- **Обработка ошибок:** нет `return` после `httpx.WriteError`; ошибка
  проглочена через `_`; неверный `apperr.Kind` — ошибка клиента отдаётся как 500
  или наоборот; доменная ошибка обёрнута `apperr.Wrap` и потеряла свой класс;
  ошибки сравниваются через `==`.
- **Потерянное «не найдено»:** `UPDATE` или `DELETE` без проверки
  `RowsAffected`; `sql.ErrNoRows` не переведён в доменную ошибку; нарушение
  внешнего ключа (код `23503`) уходит 500-й.
- **Конкурентность:** проверка и запись разными запросами без транзакции и
  блокировки; лимит через `==` вместо `>=`; общие данные без синхронизации.
- **Валидация:** проверяются старые значения вместо новых; проверка в слое, где
  ей не место по CLAUDE.md.
- **SQL:** склейка строк вместо плейсхолдеров; незакрытые `rows`.
- **Контекст:** `context.Background()` внутри слоёв; внешний вызов без
  контекста или таймаута.
- **Идемпотентность:** повторный вызов или повторная доставка события дублирует
  эффект — деньги, резервы, кошельки.
- **Изменение поведения в «рефакторинге»:** сравни старый и новый путь кода —
  статусы, коды ошибок, побочные эффекты.
- **Явные нарушения CLAUDE.md** — только если можешь процитировать правило.

Не пиши про:

- стиль, форматирование, имена, порядок импортов — это проверяет golangci-lint
  в CI;
- «можно было бы лучше» и вкусовые предложения;
- то, что зависит от неизвестных входных данных или состояния, если не можешь
  показать конкретный сценарий поломки.

## 4. Проверь каждую находку

Перечитай код ещё раз и убедись, что проблема реальна: найди строку, где она
проявляется, и сценарий, при котором она срабатывает. Не уверен — выбрось.

## 5. Итог в терминал

Список находок или фраза «Ошибок в логике и нарушений CLAUDE.md не нашёл».

Если флага `--comment` нет — на этом всё, в GitHub ничего не публикуй.

## 6. Публикация — только с `--comment`

- **Находок нет** — один комментарий:
  `gh pr comment N --repo owner/repo --body "Проверил: ошибок в логике и нарушений CLAUDE.md не нашёл."`
- **Находки есть** — по одному инлайн-комментарию на каждую через
  `mcp__github_inline_comment__create_inline_comment` с `confirmed: true`, на
  строке, где проблема проявляется.

Каждый комментарий — на русском, на «ты», из трёх частей:

1. что не так — одной фразой;
2. к чему приведёт — конкретно: какой статус получит клиент, что запишется в
   базу, в какой ситуации сломается;
3. как исправить.

Блок `suggestion` — только если он целиком исправляет проблему и не длиннее
пяти строк. Одна проблема — один комментарий.

Ты только комментируешь: не апрувь, не запрашивай изменения, не правь файлы и
не пушь код.
