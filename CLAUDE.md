# GoMarket — правила проекта

Монорепо интернет-магазина на микросервисах. Пять сервисов: `identity`,
`catalog`, `cart`, `payment`, `order`, плюс NGINX-gateway. Эталон, с которого
копируется любой новый сервис, — `services/example`.

Правила ниже обязательны. Они проверяются линтером, CI и на ревью.

## Структура

```
services/<name>/
  cmd/main.go              точка входа: сборка зависимостей и graceful shutdown
  internal/config/         конфигурация сервиса
  internal/entity/         доменные типы и доменные ошибки
  internal/handler/        HTTP: разбор запроса, DTO, роутер
  internal/service/        бизнес-логика
  internal/repository/     доступ к базе
  migrations/              goose-миграции
shared/                    общий код: apperr, config, httpx, logging, metrics, postgres
proto/                     контракты gRPC и схемы событий
```

## Слои и направление зависимостей

Зависимости направлены только внутрь, к домену:

```
handler → service → repository
              ↓         ↓
            entity ← ─ ─┘
```

- `handler` не ходит в `repository` напрямую и не содержит бизнес-правил;
- `repository` не знает про `service` и про HTTP;
- `entity` не импортирует ничего из слоёв выше — поэтому доменные ошибки
  живут именно там;
- зависимости передаются интерфейсами через конструкторы, никаких глобальных
  переменных и синглтонов;
- интерфейс объявляет **потребитель**: `service` описывает нужный ему
  `Repository` у себя, а не импортирует чужую абстракцию.

## Ошибки

- наружу из `service` возвращается только `*apperr.Error`;
- техническая ошибка оборачивается: `apperr.Wrap(err, kind, code, message)` —
  причина остаётся в цепочке и попадает в лог, но клиенту не показывается;
- обычная обёртка внутри слоя — `fmt.Errorf("что делали: %w", err)`, всегда с `%w`;
- сравнение только через `errors.Is` / `errors.As`, никогда по строке;
- `handler` не выбирает HTTP-статус сам — отдаёт ошибку в `httpx.WriteError`;
- `code` в ответе — часть публичного контракта, менять можно только вместе
  с версией API.

## Контекст

- `context.Context` — первый параметр любой функции, которая ходит в базу,
  в сеть или к другому сервису;
- `context.Background()` внутри слоёв запрещён, кроме `main` и graceful shutdown;
- на каждый внешний вызов — таймаут;
- контекст не хранится в структурах.

## Логирование

- только `log/slog` через `shared/logging`, формат один на весь проект;
- в обработчиках используются методы с контекстом (`log.InfoContext`) —
  тогда `request_id` подмешивается автоматически;
- ключевые поля: `request_id`, `user_id`, `order_id`;
- в логи не попадают пароли, токены и тела запросов;
- `fmt.Println` и `log.Printf` в рабочем коде запрещены.

## Конфигурация

- всё из переменных окружения через `shared/config.Load[T]` и теги
  `env:"NAME, default=..."`;
- никаких значений по умолчанию, зашитых в код мимо конфигурации;
- секреты не коммитятся; образец переменных — в `.env.example`.

## База

- database-per-service: своя база у каждого сервиса, ходить в чужую запрещено;
- межсервисное общение только по gRPC или через Kafka;
- только параметризованные запросы, склейка SQL строками запрещена;
- миграции goose, обязательно обратимые — секция `-- +goose Down` не пустая;
- денежные суммы — целые в копейках (`int64`), никогда `float`.

## Тесты

- покрытие бизнес-логики не ниже 70%, CI падает ниже порога;
- тесты табличные, подтесты через `t.Run`, имена подтестов на русском
  и описывают поведение, а не метод;
- тестовый пакет с суффиксом `_test` — тест видит только публичный API;
- зависимости подменяются заглушками или моками (`mockery`), тест бизнес-логики
  не ходит в базу;
- `t.Parallel()` там, где тест не делит состояние;
- проверяется и результат, и то, с какими аргументами позвали зависимость.

## HTTP

- роутер chi, единый формат ошибки из `shared/httpx`;
- наружу отдаются DTO обработчика, а не доменные сущности;
- валидация входных данных на границе, в `handler` или в начале `service`;
- у каждого сервиса есть `/healthz`, `/readyz` и `/metrics`;
- `/healthz` не ходит в зависимости, `/readyz` — ходит;
- `user_id` и роли берутся из заголовков, которые проставил Gateway;
  токен повторно не проверяется.

## Стиль

- комментарии на русском, код и идентификаторы на английском;
- комментарий объясняет «почему», а не «что» — что делает код, видно из кода;
- экспортируемые типы и функции с нетривиальным поведением документируются;
- имена без сокращений: `widgetRepository`, а не `wr`;
- ошибки именуются `ErrSomething`, интерфейсы — по роли (`WidgetRepository`),
  без префикса `I`.

## Git

- ветки от `develop`, имя `feature/TASK-ID-краткое-описание`;
- коммиты в формате Conventional Commits: `feat:`, `fix:`, `refactor:`, `test:`,
  `docs:`, `chore:`;
- PR в `develop`, с номером задачи в заголовке;
- PR не мержится без зелёного CI и апрува второго разработчика;
- `shared/`, `proto/`, `.github/` и `services/order/` требуют апрува ментора.

## Чего не делать

- не паниковать в рабочем коде — возвращать ошибку;
- не игнорировать ошибки через `_`, кроме осознанных случаев с комментарием;
- не тащить новую библиотеку без обсуждения: стек зафиксирован (chi, sqlx,
  goose, pgx, go-envconfig, kafka-go, slog, testify, mockery, buf);
- не писать в чужую базу и не импортировать `internal/` чужого сервиса;
- не коммитить сгенерированные моки и protobuf без необходимости — они
  собираются командой `task gen`.

## Команды

```
task up         поднять инфраструктуру
task check      всё, что проверит CI: формат, линтер, тесты, покрытие
task test       тесты с детектором гонок
task gen        protobuf и моки
task migrate:up -- example    накатить миграции сервиса
```
