## 1. Что мы строим

Интернет-магазин на микросервисах: каталог, корзина, заказы с резервированием
товара и оплатой с внутреннего кошелька.

Магазин — повод, а не цель. Цель — руками пройти то, из чего состоят настоящие
распределённые системы: синхронные вызовы по gRPC, события через Kafka,
**сагу** с компенсациями, идемпотентность, outbox, ретраи и circuit breaker,
метрики и логи, по которым можно найти, что случилось с конкретным заказом.

Скоуп урезан относительно полного README: **пять сервисов**, а Notification,
поиск, аналитика и трейсинг — в бэклоге. Порядок работ выстроен так, чтобы до
саги добраться к пятой неделе, а не в конце.

## 3. Сервисы

```
                    клиент
                      │ HTTPS
                      ▼
        ┌──────────────────────────┐   проверка токена
        │   Gateway (NGINX)        │──────────────────▶ Identity
        │   маршруты, RBAC, 429    │
        └──┬─────────┬─────────┬───┘
           │         │         │      X-User-Id, X-User-Roles, X-Request-Id
           ▼         ▼         ▼
       Catalog ◀─── Cart ◀─── Order ───▶ Payment
           ▲    gRPC     gRPC   │   gRPC
           └────────────────────┘
                 gRPC: резервы

      Kafka: user_registered, order_created, order_paid, order_cancelled,
             payment_completed, payment_failed
```

### Gateway (NGINX) — зона Феди

Единая точка входа. Маршрутизирует запросы, для каждого проверяет токен в
Identity, закрывает ручки по ролям (401 без токена, 403 при чужой роли),
ограничивает частоту (429). Внутренним сервисам прокидывает заголовки
`X-User-Id`, `X-User-Roles`, `X-Request-Id` — **сервисы им доверяют и токен
повторно не проверяют**.

### Identity — пользователи и аутентификация

User и Auth из полного README объединены в один сервис.

- регистрация: имя, email, телефон, пароль (хэш bcrypt или argon2), роль
  Customer по умолчанию; публикует `user_registered`;
- логин: пара токенов — access (15–30 минут, с `user_id` и ролями) и refresh
  (7–30 дней); активные токены хранятся в Redis с TTL;
- проверка токена для Gateway: подпись, срок, активность в Redis → `user_id` и
  роли;
- обмен refresh-токена на новую пару, logout (инвалидация обоих);
- профиль, смена пароля, soft-delete; назначение ролей Manager и Analyst админом.

В бэклоге: ротация refresh-токенов.

### Catalog — товары и остатки

- товары и категории: CRUD для Manager, публичный список с пагинацией и
  фильтрами (категория, диапазон цены);
- остатки: продать ниже нуля нельзя;
- **резервирование для Order (gRPC):**
  - `Reserve(order_id, items)` — резервирует все позиции атомарно или отклоняет
    целиком; повторный вызов с тем же `order_id` ничего не делает;
  - `ConfirmReservation(order_id)` — списывает резерв в продажу;
  - `ReleaseReservation(order_id)` — возвращает резерв (компенсация);
  - резерв живёт ~15 минут, протухшие освобождает фоновый процесс.

### Cart — корзина

Эволюция вашего Cart API.

- одна активная корзина на пользователя, `user_id` — из заголовка Gateway;
- позиции ссылаются на `product_id`; при добавлении цена и наличие проверяются в
  Catalog по gRPC;
- чтение корзины через кэш в Redis (cache-aside, TTL, инвалидация при изменении);
- `GetCartSnapshot(user_id)` для Order (gRPC) — фиксирует состав и цены на
  момент оформления;
- по событию `order_created` корзина очищается, повторная доставка события
  ничего не ломает.

### Payment — кошельки и деньги

- кошелёк создаётся автоматически по событию `user_registered`;
- пополнение — заглушка, без реального платёжного провайдера;
- `Charge(order_id, user_id, amount)` — списание в транзакции, **повторный вызов
  с тем же `order_id` не спишет дважды**; нехватка средств — отдельная доменная
  ошибка;
- `Refund(order_id)` — возврат, компенсирующая операция, тоже идемпотентна;
- история и аудит всех денежных операций;
- **outbox:** события `payment_completed` и `payment_failed` пишутся в таблицу в
  той же транзакции, что и деньги, а фоновый процесс публикует их в Kafka.

### Order — заказы и сага

- оформление из снапшота корзины; пустая корзина — ошибка;
- статусы: `created → reserved → paid → completed`, или `cancelled` с причиной;
- **оркестратор саги** — см. ниже;
- отмена пользователем до `paid` запускает компенсации;
- история заказов с кэшем последних в Redis;
- события `order_created`, `order_paid`, `order_cancelled`.

### Сага оформления заказа

```
[1] создать заказ (created), событие order_created
 │
 ▼
[2] Catalog.Reserve        ── ошибка ──▶ cancelled: нет товара
 │   reserved
 ▼
[3] Payment.Charge         ── ошибка ──▶ компенсация Catalog.ReleaseReservation
 │   paid                                → cancelled: нет средств
 ▼
[4] Catalog.ConfirmReservation
     completed, событие order_paid
```

Каждый шаг идемпотентен по `order_id`, состояние саги хранится в базе Order и
переживает рестарт. На каждый gRPC-вызов — таймаут; ретраи — только на
временные ошибки (`Unavailable`, `DeadlineExceeded`), бизнес-ошибки не
ретраятся; на клиентах Catalog и Payment — circuit breaker. Незавершённые саги
после рестарта добивает или компенсирует фоновый процесс.

### Как сервисы общаются

**Синхронно, gRPC:** Gateway → Identity (проверка токена), Cart → Catalog
(цены и наличие), Order → Cart (снапшот), Order → Catalog (резервы),
Order → Payment (списание и возврат).

**Асинхронно, Kafka:**

| Событие | Публикует | Слушает |
|---|---|---|
| `user_registered` | Identity | Payment (создать кошелёк) |
| `order_created` | Order | Cart (очистить корзину) |
| `order_paid`, `order_cancelled` | Order | пока никто; Notification и аналитика — в бэклоге |
| `payment_completed`, `payment_failed` | Payment, через outbox | Order |

Доставка «хотя бы один раз», поэтому **каждый консьюмер идемпотентен**:
повторное сообщение не должно создать второй кошелёк или очистить уже новую
корзину.

**Данные:** у каждого сервиса своя база. Ходить в чужую запрещено — только
через gRPC или события.

### Порты при локальном запуске

| Сервис | HTTP |

| example | 8080 |
| identity | 8081 |
| catalog | 8082 |

## 4. Устройство репозитория

```
.github/            CI, ревью-бот, CODEOWNERS, шаблон PR
deploy/             docker-compose и конфиги инфраструктуры
docs/               онбординг, ADR (docs/adr), документы ментора
proto/              контракты gRPC и схемы событий Kafka
scripts/            скрипты для CI и Taskfile
services/
  example/          эталонный сервис — образец для копирования, не деплоится
  identity/ catalog/ cart/ payment/ order/
shared/             общий код всех сервисов
CLAUDE.md           правила кода — обязательны
Taskfile.yml        все команды проекта
```

Монорепо: один `go.mod` на всё. Одна версия каждой зависимости, `shared/`
подключается напрямую, контракт и обоих его участников можно поменять в одном
PR.

Границу между сервисами держит компилятор: пакет `services/order/internal/...`
невозможно импортировать из `services/catalog/` — это правило `internal/` в Go.

### Внутри сервиса

```
services/<имя>/
  cmd/main.go            сборка зависимостей, запуск, graceful shutdown
  internal/config/       конфигурация
  internal/entity/       доменные типы и доменные ошибки
  internal/handler/      HTTP: разбор запроса, DTO, роутер
  internal/service/      бизнес-логика
  internal/repository/   доступ к базе
  migrations/            goose-миграции
  Dockerfile
```

Зависимости направлены только внутрь:

```
handler → service → repository
              ↓          ↓
            entity ◀─────┘
```

| Слой | Что делает | Чего не делает |
|---|---|---|
| `handler` | разбирает запрос, валидирует формат входа, вызывает сервис, переводит результат в DTO ответа | бизнес-правила, SQL, выбор HTTP-статуса по ошибке (это `httpx.WriteError`) |
| `service` | бизнес-правила: лимиты, переходы статусов, сага; координирует репозитории и клиенты | ничего не знает про HTTP и SQL |
| `repository` | SQL, перевод ошибок базы в доменные | бизнес-правила, валидация |
| `entity` | доменные типы и ошибки | не импортирует ничего из слоёв выше |

Подробно — в [`CLAUDE.md`](../CLAUDE.md), живой пример — в
[`services/example`](../services/example), общие пакеты — в
[`shared/README.md`](../shared/README.md).

## 5. Первый день: окружение

### Что поставить

- **Go 1.26.** Проверь `go version`. Если тесты пишут
  `compile: version "go1.26.0" does not match go tool version`, у тебя
  смешались две версии Go: старая в системе и подкачанная автоматически.
  Поставь 1.26 полностью (`brew install go` или пакет с go.dev), а не через
  автоподкачку;
- **Docker** — Docker Desktop, OrbStack или Colima;
- **Task** — `brew install go-task`;
- желательно **gh** — `brew install gh`, для работы с PR из терминала.

### Запуск

```bash
git clone git@github.com:go-trainee-techcore/go-market.git
cd go-market

task tools                 # golangci-lint, goose, mockery, buf
cp .env.example .env       # .env в git не попадает
task up                    # Postgres, Redis, Redpanda, Prometheus, Grafana
task migrate:up -- example

set -a; source .env; set +a
POSTGRES_DB=example go run ./services/example/cmd
```

`task tools` ставит инструменты в `$(go env GOPATH)/bin` — эта папка должна быть
в `PATH`.

Проверка, что всё живо — команды `curl` в
[`services/example/README.md`](../services/example/README.md). Дальше:

| Что | Где |
|---|---|
| Grafana | http://localhost:3000, `admin` / `admin` |
| Prometheus | http://localhost:9090 |
| Redpanda Console (Kafka) | http://localhost:8090 |
| PostgreSQL | `localhost:5432`, `gomarket` / `gomarket`, база на каждый сервис |
| Redis | `localhost:6379` |
| Kafka | `localhost:9092` |

И главное:

```bash
task check
```

Это то же, что проверит CI: формат, линтер, тесты с детектором гонок и порог
покрытия. **Зелёный `task check` перед каждым пушем.**

### Если что-то не так

- **Порт занят.** Что-то уже слушает 5432 или 3000 — останови локальный Postgres
  или Grafana.
- **Нет базы сервиса.** Базы создаются только при первом запуске Postgres на
  пустом томе. `task clean && task up` пересоздаст всё с нуля (данные пропадут).
- **Сервис не стартует и пишет про переменную.** Не выполнен
  `set -a; source .env; set +a`, или переменной нет в `.env`. Сравни с
  `.env.example`.

## 6. От задачи до мержа

1. **Задача** — на доске GitHub Projects. Взял — назначь себя и перенеси в
   *In progress*.
2. **Ветка** от `develop`: `feature/<номер-задачи>-краткое-описание`.
3. **Коммиты** — Conventional Commits: `feat:`, `fix:`, `refactor:`, `test:`,
   `docs:`, `chore:`.
4. **`task check`** — зелёный перед пушем.
5. **PR в `develop`.** Заголовок тоже в формате Conventional Commits: при мерже
   PR схлопывается в один коммит, и заголовок становится его сообщением.
   Заполни шаблон, особенно «Как проверить» — ревьюер должен суметь повторить.
6. **Автоматика.** PR не смотрят, пока она не зелёная:

   | Проверка | Что делает |
   |---|---|
   | Линтер | golangci-lint по всему репозиторию |
   | Тесты | `go mod tidy` ничего не меняет; тесты с `-race`; покрытие пакетов `internal/service` не ниже 70% |
   | Контракты | `buf lint` и `buf breaking` — запускается, только если есть `.proto` |
   | gitleaks | поиск секретов в коде и истории |
   | Ревью от Claude | инлайн-комментарии к диффу при открытии PR |

7. **Ревью-бота разбери:** исправь или ответь в треде, почему нет. Бот ошибается,
   но молча игнорировать нельзя. Повторное ревью после правок — комментарий с
   `@claude` и просьбой.
8. **Ревью напарника — обязательно.** Новый пуш сбрасывает апрув: после правок
   нужен повторный.
9. **Пути ментора.** PR, который трогает `shared/`, `proto/`, `.github/`,
   `deploy/`, `scripts/`, `CLAUDE.md`, `Taskfile.yml`, `services/order/` или
   `services/example/`, требует апрува ментора — так настроен
   [`CODEOWNERS`](../.github/CODEOWNERS). Остальное мержите сами.
10. **Все треды закрыты → squash merge.** Ветка удаляется сама.

**Релиз** — PR из `develop` в `main`. Открывает кто-то из вас, апрувит ментор,
мерж обычным merge-коммитом: так `develop` и `main` не расходятся.

**Черновик PR** (draft) — чтобы показать работу рано и получить обратную связь.
Бот черновики не ревьюит.

### Как ревьюить напарника

- **Корректность:** что будет на пустом вводе, на несуществующем id, при двух
  параллельных запросах, при ошибке базы?
- **Ошибки:** доменные, правильный класс, после `WriteError` есть `return`.
- **Слои:** правило там, где ему место; хендлер не ходит в репозиторий.
- **Тесты:** проверяют поведение, а не реализацию; есть негативные случаи.
- **Читаемость:** через месяц ты сможешь это поменять, не спрашивая автора?

Пиши, **что** не так и **почему**, а не «переделай». Мелочь помечай как
мелочь — тогда автор понимает, что блокирует мерж, а что нет.

## 7. Контракты прежде кода

Все межсервисные интерфейсы описаны в [`proto/`](../proto): gRPC-методы и схемы
событий Kafka. Публичный REST — в OpenAPI.

- контракт меняется **до** реализации, отдельным PR, с апрувом ментора;
- `buf breaking` в CI сравнивает с `develop`: сломать чужой контракт молча не
  получится;
- **первая неделя — только контракты.** Кода будет мало, и это будет ощущаться
  как «ничего не делаем». Это нормально: после неё каждый сервис — коробка с
  фиксированным интерфейсом, и вы не блокируете друг друга.

## 8. Правила работы с AI

AI в проекте есть и в ревью, и у вас в редакторе. Правила такие.

**Можно:** просить объяснить, разбирать свои ошибки, писать boilerplate — моки,
миграции, маппинг DTO, документацию, табличные тесты по готовому поведению.

**Нельзя в первом подходе:** отдавать AI ту логику, ради которой проект
затевался, — конкурентность, идемпотентность, сагу, outbox. Сначала ломаете об
неё голову сами, потом можно сверяться.

**Главное правило:** любой свой PR ты должен суметь объяснить голосом за пять
минут — почему так и какие были альтернативы. Не можешь — PR возвращается,
независимо от того, кто его писал. Раз в неделю ментор выборочно просит такое
объяснение.

[`CLAUDE.md`](../CLAUDE.md) читает и ревью-бот, и ваш Claude в редакторе:
советы будут в стиле проекта.

## 9. Ритм и общение

| Когда | Что |
|---|---|
| Понедельник, 30 минут | планирование: задачи на неделю пишете вы, ментор апрувит |
| Четверг, час | демо сделанного за неделю + один архитектурный разбор |
| Всё остальное время | асинхронно |

- **Вопросы — в PR или issue, не в личку.** Ответ остаётся для обоих и для
  того, кто придёт после.
- **Застрял:** час пробуешь сам, потом issue: что делаешь, что пробовал, что
  видишь. Если нужен именно ментор — метка `needs-mentor`.
- **Принял решение, у которого были альтернативы** — короткий ADR в
  [`docs/adr`](adr), по [шаблону](adr/0001-template.md). Полстраницы хватает.
- **Ментора нет, а решение нужно:** выбирайте самый простой вариант, который не
  меняет контракты, пишите ADR и двигайтесь дальше. Стоять неделю хуже, чем
  потом переделать.

## 10. План по неделям

| Недели | Что |
|---|---|
| 1 | контракты: все `.proto`, OpenAPI, коды ошибок, схемы событий |
| 2–3 | Cart — вместе, слиянием двух Cart API в монорепо; параллельно Identity |
| 3–5 | Catalog и Payment, по одному на каждого |
| 5–8 | Order и сага — вместе |
| 8+ | наблюдаемость, Kubernetes, хаос-тесты |

**MVP — минимум для завершения стажировки.** Сквозной сценарий работает через
Gateway и виден на дашборде:

1. регистрация → кошелёк создался сам → логин;
2. Manager наполняет каталог, Customer собирает корзину (с кэшем);
3. пополнение кошелька → оформление → сага: резерв → списание → подтверждение →
   `completed`;
4. нет товара или нет средств → корректные компенсации и `cancelled`;
5. Payment или Catalog падает → ретраи и брейкер отрабатывают, система не
   зависает, заказ добивается или компенсируется;
6. метрики и алерты отражают происходящее, по `order_id` заказ находится в логах.

## 11. Ошибки, которые уже встречались

Собрано из ревью Cart API. Каждая из них — реальный баг, а не стиль.

- **Сервис при ошибке старта выходит с кодом 0.** В Kubernetes упавший сервис
  выглядит как успешно завершённый. Вся работа — в `run() error`, в `main` —
  `os.Exit(1)` при ошибке, как в эталоне.
- **Валидация не в том слое.** Формат входа — в хендлере, бизнес-правила — в
  сервисе. В репозитории проверок нет.
- **Проверяются старые значения вместо новых.** При обновлении валидируется то,
  что пришло в запросе, а не то, что прочитано из базы.
- **Нарушение внешнего ключа превращается в 500.** Ссылка на несуществующую
  запись — ошибка клиента: разбери код PostgreSQL и верни доменную ошибку
  (см. `shared/README.md`).
- **Нет `return` после записи ошибки.** Код идёт дальше и пишет второй ответ.
- **Проверка и вставка разными запросами.** Два параллельных запроса оба
  проходят проверку лимита. Нужна транзакция с блокировкой. И лимит —
  `count >= max`, а не `count == max`: после одной гонки `==` перестаёт
  срабатывать совсем.
- **Одна ошибка объявлена в двух местах с разными правилами.**
- **Мёртвые ветки:** обработка ошибки, которую никто не возвращает;
  `sql.ErrNoRows` после `SelectContext`.
- **Скопированные подписи в обёртках ошибок** указывают не на тот метод.
- **Тест закрепляет баг:** мок отдаёт состояние, которое в реальности
  невозможно, и тест проверяет реакцию на него.
- **Тест печатает пароль.** Логи CI в публичной репе видны всем.
- **`fmt.Println` в рабочем коде.**

## 12. Словарь

| Термин | Что значит |
|---|---|
| сага | длинная операция из шагов в разных сервисах без общей транзакции; при сбое уже сделанные шаги отменяются компенсациями |
| компенсация | действие, отменяющее эффект шага: снять резерв, вернуть деньги |
| идемпотентность | повторный вызов с теми же данными не меняет результат: второй `Charge` с тем же `order_id` не спишет деньги ещё раз |
| at-least-once | сообщение доставят хотя бы один раз, но могут и дважды — поэтому консьюмеры идемпотентны |
| outbox | событие пишется в таблицу в той же транзакции, что и данные, а отдельный процесс публикует его в Kafka. Иначе можно списать деньги и не отправить событие |
| DLQ | очередь для сообщений, которые не удалось обработать после N попыток |
| circuit breaker | после серии ошибок перестаёт звать упавший сервис и сразу возвращает ошибку, давая тому восстановиться |
| backoff + jitter | пауза между ретраями растёт и чуть случайна, чтобы клиенты не долбили сервис синхронно |
| cache-aside | читаем из кэша; промах — читаем из базы и кладём в кэш; при изменении кэш сбрасываем |
| RED-метрики | Rate, Errors, Duration — минимум метрик для любого сервиса |
| `request_id` | идентификатор запроса, по которому он находится в логах всех сервисов |
| ADR | Architecture Decision Record — короткая запись о принятом решении и его причинах |
