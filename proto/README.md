# Контракты

Здесь живут все `.proto`: межсервисные gRPC-методы и схемы событий Kafka.

Правила:

- контракт меняется **до** реализации, отдельным PR, с апрувом ментора;
- `buf breaking` в CI сравнивает с `develop` — сломать чужой контракт молча
  не получится;
- сгенерированный код лежит в `proto/gen` и собирается командой `task gen`.

```
proto/
  identity/v1/
  catalog/v1/
  cart/v1/
  payment/v1/
  order/v1/
  events/v1/     схемы событий Kafka
```

## События Kafka

Схемы — в [`events/v1`](events/v1), по одному файлу на событие.

### Кто публикует — кто слушает

| Событие | Топик | Ключ партиции | Публикует | Слушает |
|---|---|---|---|---|
| `user_registered` | `user.registered.v1` | `user_id` | Identity | Payment (создать кошелёк) |
| `order_created` | `order.created.v1` | `order_id` | Order | Cart (очистить корзину) |
| `order_paid` | `order.paid.v1` | `order_id` | Order | пока никто (Notification и аналитика — в бэклоге) |
| `order_cancelled` | `order.cancelled.v1` | `order_id` | Order | пока никто (Notification и аналитика — в бэклоге) |
| `payment_completed` | `payment.completed.v1` | `order_id` | Payment, через outbox | Order |
| `payment_failed` | `payment.failed.v1` | `order_id` | Payment, через outbox | Order |

### Общий конверт

Каждое событие начинается с поля `EventMetadata metadata = 1`
([`events/v1/metadata.proto`](events/v1/metadata.proto)):

| Поле | Зачем |
|---|---|
| `event_id` | UUID события, ключ идемпотентности консьюмера |
| `occurred_at` | когда произошёл бизнес-факт (не время отправки в Kafka) |
| `source` | сервис-публикатор: `IDENTITY`, `ORDER` или `PAYMENT` |
| `request_id` | `X-Request-Id` исходного запроса, чтобы найти событие в логах; может быть пустым |

`event_id` создаётся один раз, при появлении события. У Payment это момент записи
строки в outbox, а не момент отправки в Kafka. Повторная публикация после сбоя
несёт тот же `event_id`, и консьюмер отбрасывает дубль.

### Правила

**Имена топиков.** Формат `<сущность>.<что случилось>.v1`: имя события
`user_registered` превращается в `user.registered`. Суффикс `.v1` совпадает с
версией пакета в `proto`. Ломающее изменение схемы — это новый топик `.v2`, а не
правка старого.

**Ключ партиции.** Ключ — строка `order_id` (для `user_registered` — `user_id`),
передаётся как есть, не в protobuf. Kafka гарантирует порядок только внутри
одной партиции **одного топика**. Все сообщения одного заказа в одном топике идут
по порядку. Порядка между разными топиками (например, `order.paid.v1` и
`order.cancelled.v1`) нет. Сейчас этого никто не требует, но Notification и
аналитике это надо учесть.

**Значение сообщения** — protobuf-сериализованное событие.

**Идемпотентность.** Доставка «хотя бы один раз», поэтому каждый консьюмер:

1. сохраняет обработанные `event_id` в своей базе в той же транзакции, что и
   результат обработки, и при повторе ничего не делает;
2. не полагается только на `event_id`: у действия есть собственная защита (один
   кошелёк на `user_id`; очистка только той корзины, чей `cart_id` пришёл в
   `order_created`).

**DLQ.** Сообщение, которое не удалось обработать после N попыток, уходит в
`<топик>.<группа-консьюмера>.dlq`. Число попыток и реализацию определяем при
написании первого консьюмера.

**Совместимость.** Внутри `v1` можно только добавлять поля. Удалять, менять тип
и переиспользовать номера нельзя: `buf breaking` это не пропустит.

**Деньги** — `int64` в минимальных единицах валюты (копейки), без `float`.
